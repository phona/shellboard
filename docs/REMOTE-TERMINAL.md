# 远程终端:探索记录、缺陷修复与能力边界

> 前置阅读:`docs/ARCHITECTURE.md` §4 D5 / D7 —— 本文是它的补充与修正。
> 本文记录一次围绕"直播输出时读历史"的完整技术探索:走过哪些路、为何否决、修了哪些缺陷、以及这套架构**做不到**什么。

所有结论都附实测数据或可复现命令。推测与已验证的事实分开标注。

---

## 1. 问题陈述

**Agent 直播输出时,用户上划去读历史,读到的是损坏的内容。**

具体症状(用户截图 + 复现):

- 行在词中间截断,余下部分掉到下一行
- `... +N lines (ctrl+o to expand)` 折叠标记出现在不属于它的位置
- 同一段消息的多个中间渲染状态叠在一起
- 集中在"旧消息 ↔ 正在刷新的新消息"的交界处
- 校准修复后,能被滚到的历史突然变短

### 1.1 根因链

```
agent 应用有自己的模型(Ink/React 树),每次状态变化整体重渲染
   ↓ 实测:一条 60 行回复的 wire ≈ 176 KB,约 60 次重绘,每次 2.9 KB
tmux 把每次重绘作为屏幕变更转发
   ↓ 字节流到达客户端
xterm 客户端累积进自己的 scrollback
   ↓
scrollback 里堆着重绘的每个中间态,与 pane 真相漂移
```

三级投影,冗余在第一级就产生了。D7 已记录此模型,但当时认定"客户端 scrollback 是 pane 真相的缓存,需要时重新拉取"——**重新拉取的机制从未被实现**。

## 2. 探索:走过和被否决的路

### 2.1 滚动触发校准(已采用)

用户停止滚动 400ms 后,客户端请求服务端重新拉取 pane 真相,替换整个缓冲。

- 优点:不碰架构、不碰红线、服务端零新组件
- 缺点:每次校准都是整缓冲 wipe + 重绘(见 §4)

### 2.2 双状态机 / 服务端 checkpoint(已否决)

服务端起一个 `@xterm/headless`,吃同一条字节流,serialize 成 checkpoint;客户端 reset + 重放。

否决理由(按重要性):

1. **修不了这个问题。** 服务端模型是字节派生的,继承同样的漂移。它让客户端和服务端**达成一致**,不是与 pane 真相一致。
2. **alt buffer 结构性分叉。** 客户端刻意吞掉 DECSET 1049(`useTerminalWs.ts` 的 `privateModes`),服务端模型没有理由吞。vim/less/codex 一开,两边状态从根本上不一致。
3. **D5 让场景不成立。** socket 断开即杀 PTY,断开期间没有字节流可喂模型;重连时只能 `capture-pane` 重建——那不如直接 `capture-pane`。
4. **关掉唯一的自动纠正。** 现在每次重连都是一次免费的全量重同步。

### 2.3 AOE 的 VT Live Transport(研究过,部分采纳)

`agent-of-empires` 的 `src/tmux/vt.rs`:`tmux pipe-pane` 喂一个 in-process `vt100::Parser`,按光标比对检测分歧,超过就 reseed。

**采纳的:** probe 前后一致性检查(见 §3.4)。

**未采纳的:** 整体架构——它的客户端是 `lines: string[]` + `applyPatch`,没有 cell grid。我一度据此判断它"没有宽度处理",**这是错的**:它有 `textWidth` / `graphemeWidth` / `clusterSpanAt`,还用固定宽度 inline-box 防字体回退导致列漂移。但它是 DOM 文本渲染而非终端仿真器,且用户实测"越加载越卡"。

AOE "越加载越卡"的成因已定位(其仓库 `src/server/live_ws.rs` + `web/src/hooks/useLiveTerminal.ts`):每帧的成本随历史长度线性增长,有四处——`plan_patch` 每次发布 diff 整个 window、`last_sent` 每次发布克隆每一行、`applyPatch` 每个补丁重新分配整个历史数组、20 帧/秒。H=4000 时每秒 32 万次操作,v viewer 各一份。

### 2.4 tmux copy-mode(未采纳)

滚动走 tmux 的 copy-mode,客户端不持有 scrollback。

- 唯一能同时做到"零闪烁 + 内容精确"的路——因为结构上不存在"客户端缓存错了"
- 否决理由:D7 立身之本是即时本地滚动(零网络往返)。每次滚动手势走网络,且 copy-mode 的搜索/跳转交互模型和浏览器原生滚动差异大
- 这是**产品决策**,不是工程优化

### 2.5 koko 栈(已否决)

读过 `jumpserver/koko` 源码。它的浏览器路径和 Shellboard 一样是字节中继(其 `pkg/httpd/userwebsocket.go` 二进制帧原样转发),服务端 VT(`internal/sessiontools/terminal_observer.go`,200 行 scrollback)只用于**给 agent 提取命令输出文本**,从不发给终端视图。

- 换过去不会解决任何问题,反而丢掉 tmux 这个真相源
- 它的服务端 VT 恰恰是 Shellboard D8 红线禁止的"从字节流提取语义"

## 3. 修复的缺陷

每个缺陷都附测试。测试一律先确认"关掉修复就失败"。

### 3.1 D7 校准机制是死代码

`historyReconcile.ts` 带着完整单测,但 `decideReconcile` 从未被任何地方调用。所有测试都是绿的,而机制不存在。这是 coverage 工具要解决的第一个问题。

修:接进 `onScroll`。

### 3.2 重新播种把捕获窗口重播到快照上

`startHold` 先开保持再捕获,导致 `[T_req, T_cap]` 的字节**已经包含在快照里**,flush 时重播 → 接缝处历史重复。

修:**先捕获、再开保持。** 种子是快照,跟在后面的每个字节都严格新于它。

> 试过并否决:捕获期间 `pty.pause()`。错在 pause 停的是 node-pty 对 pty 的*读取*,不是 pane 的*写入*——pane 继续累积,快照反而比被持有的字节更新,重叠从 30ms 变成 3 秒。

### 3.3 校准把用户缓冲砍断(此缺陷由症状级测试发现)

深度固定 500,而校准**替换整个缓冲**——拉多深,之后就有多少历史。距底 800 行的读者拿到 500 行种子,恢复被 clamp,被扔到不含他正在读内容的缓冲顶部。

修:
- 深度跟随读者:`clamp(offsetFromBottom + rows + 40, 500, 800)`
- floor 取旧的 500 而不是更低——**校准不允许让缓冲变浅**
- 超过 800 行的读者直接不校准,那是滚到顶生长路径的职责
- clamp 后重新打开手势门并触发生长:`scrollLines` 在 `viewportY = 0` 无法移动视口,`onScroll` 不触发,生长路径永远不会被请求——这是"滚不上去"的直接原因

### 3.4 校准在半写的 pane 上播种

capture-pane **总是返回一致的 pane 状态**(tmux 的 grid 对读者原子),所以"画一半"从不是撕裂读,而是那个瞬间 pane 真的半写。

两层防护:
- **客户端**:500ms 内有新字节就不校准(主防线)
- **服务端**:要求 pane 跨一个 200ms 窗口 + 跨捕获本身都保持静止

> 第一版守卫只有捕获侧的检查,症状级测试直接失败:`gen NNNN line 23`。原因是窗口只有一次捕获那么宽(~8ms),而 pane 每 5-10ms 才写一行,两次探测常落在同一间隙。

### 3.5 null 种子清空终端却等不到字节

种子为 null 时仍发 `seed-start{lines:0}`,客户端 `term.reset()` 然后永远等一个不会来的种子帧。

修:改发 `seed-skipped`,客户端保留现有缓冲。这也给了静默守卫一个"拒绝"的出口。

## 4. 实测数据

全部可在本机复现。终端 168×42,默认 scrollback 5000。

### 4.1 单次校准的成本

| 项 | 值 |
|---|---|
| `capture-pane -p -e -T -S -500` | 8 ms |
| 种子帧 | 44.6 KB(实测 session) |
| 客户端 `term.reset()` + 重绘 | 20.6 ms |
| 客户端停顿定时器 | 400 ms(设计值) |

深度与种子大小(实测):500 → 44.6 KB / 1000 → 88.1 KB / 4990 → 371 KB。

### 4.2 切换 session 的成本(比校准高一个量级)

| session | pane 历史 | 接入种子(深度 4990) |
|---|---|---|
| sb_8RpZab90kRs | 6223 行 | 375 KB |
| sb_T_I1KzhVxMA | 987 行 | 119 KB |
| sb_-jDjllMxlYU | 465 行 | 72 KB |

按 scrollback 档位:1000 → 73.5 KB / 5000(默认)→ 375 KB / 10000 → 503 KB(触顶)。

### 4.3 pane 真相是干净的

四个真实 session,`capture-pane` 历史的**相邻重复行数 0-1**,截断迹象 0。

`history-limit` 全部是 50000,**不是**约束。session sb_8RpZab90kRs 的 pane 就只有 6223 行历史。

> 一度误判:把"同一个 UI 标签出现 N 次"当成重复。`• thinking` × 93 是 93 个不同轮次,92 个相邻间距没有一对在 3 行以内。

### 4.4 一条 60 行回复的 wire

```
整条回复     175,729 B
重绘次数     60
平均每次     2,929 B      ← 一帧约 3 KB,不是 370 KB
平均每行     96 B
```

D7 记录的 370 KB 是同量级独立复现(合成行无颜色,真实 agent 带 SGR 更重)。

30Hz 全帧校正 = 86–308 KB/s = 0.7–2.4 Mbps,而 live 增量流本身已约 133 KB/s。**为修一个 live 路径已处理好的东西付 1–3 倍带宽。**

## 5. 能力边界

### 5.1 已抵达的硬边界

**xterm 的 scrollback 对转义序列是只读的。**

实测:`scrollToLine(5)` 后 `viewportY=5`、`\x1b[H` 后 `cursorY=0`,写入却落在第 15 行(`baseY` 处的 live 屏),不是滚到的第 5 行。三次尝试均如此,其中两次清空了别的行。

`@xterm/xterm` 6.0 的 typings 里 `loadCell` / `setCell` 零命中,`IBufferLine` 只有读方法。

**推论:**

```
字节流模型 → 客户端持有可分歧的状态 → 会漂
                                    ↓
客户端不能被打补丁 ←────────────────┘
                                    ↓
                              校正只能全量 → 全量就贵 + 闪
```

所以:**闪烁频率 = 校正频率**,这个等式在"xterm 当客户端"下去不掉。只能把校正频率压下来,不能消除单次成本。

### 5.2 能做到 / 做不到

| | 状态 |
|---|---|
| 直播路径增量、便宜 | ✅ 本来就好(只传新字节,成本与历史长度无关) |
| 历史内容可读、能拉到 pane 真相 | ✅ 已实现 |
| 即时本地滚动 | ✅ 本来就有 |
| 无闪烁 | ❌ 结构性。xterm 只给"全量重绘"一个工具 |
| 零延迟 | ❌ 每个字节过网络 |
| 滚动模型与本地等价 | ❌ 那是两种模型,不是实现差异 |

### 5.3 规模维度

**能走很远:很多 agent session,一次看一个。**
`AppLayout.tsx` 一次只挂一个 `TerminalView`(`key={selected.session.id}`),切走即卸载 → WS 关闭 → PTY 被杀。所以服务端同时只有 1 个 PTY + 1 条 WS,observer 每秒只 fork 一次 `list-sessions`,与 N 无关。§3/§4 的所有成本都是**单 session 成本,不随 agent 数倍增**。

**走不动:同时监看多个 agent。**
那需要一个标签页里 N 条 live 字节流。这是 AOE 的问题,而解法(服务端 grid + 行数组客户端)正是 Shellboard 的 xterm 客户端变不过去的。

**真正的税在切换,不在校准。** §4.2 的 375KB/次 是校准(44.6KB)的 8 倍。

## 7. 测试覆盖现状

```
pnpm --filter @shellboard/web test:coverage
pnpm --filter @shellboard/server test:coverage
```

起步时 coverage 工具根本不存在——web 29 个测试全部集中在一个模块,"策略模块被自己的测试练习"看起来就是 100%,D7 校准机制正是这样带着绿色的测试文件变成了死代码。

现在:web 语句覆盖 **16.2%**(315/1941),测试 187;server 语句覆盖 77.4%,测试 76。

`src/state` 91.6% / `src/util` 83.9% / `api/client.ts` 73% / `useEvents.ts` 93.8% / `terminal/bridge.ts` 92.7% / `terminal/wire.ts` 89.3%。

剩下未覆盖的主体是需要 DOM 的 React 组件。**不再加依赖的话,能覆盖的都已覆盖。**

### 7.1 覆盖率挖出的四个非显而易见事实

1. **zustand v5 的 persist 默认用 `window.localStorage`,不是裸全局。** 只桩后者会让 persist **静默禁用**——既不 hydrate 也不写,持久化测试全部因为错误的原因通过。
2. **`store.ts` 的 `scrollback` 故意不设 clamp**,边界归服务端。没有测试守着,容易被后人当漏写补上。
3. **`sessionRoute` 的两个一行身份守卫**(same-id hashchange 不清 `openDiff`、selection 没变不重复 `replaceState`)——都是容易顺手删掉且无测试会发现的东西。
4. **通知门是三个条件 AND**:opted in + 标签页隐藏 + working→idle 跃迁。少任何一个,要么永远不响,要么用户正盯着终端时响。

## 8. 方法论:这次最值钱的一条

**症状级测试逼出了不完整的修复。**

我为"消息断在半句"写的第一版守卫,在自己的推理里是成立的。写成"被播种的屏幕必须是一个完整世代"的症状级断言后,它第一次运行就失败——收到 `gen NNNN line 23`。

同一修复,"验证修复的测试"(忙碌 pane 上不发种子)在第一版时**开和关守卫都通过**,什么都没证明。我偶然去关守卫验证才发现。

> 正确的顺序:症状 → 失败测试 → 修 → 通过。
> 这次的顺序:症状 → 读源码得假设 → 修 → 写测试 → 通过(什么都没证明)→ 关守卫验证 → 才发现第一版测试是空的。

写测试的成本远低于带着一个"看起来修好了"的缺陷继续往下走十轮的成本。
